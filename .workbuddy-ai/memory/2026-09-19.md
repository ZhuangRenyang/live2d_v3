## Live2D 模型动作预览台（GitHub Pages 静态站点）

**目标**：把 live2d_3 的看板娘模型做成可上传 GitHub 并用 Pages 预览的网页，能逐个看动作、切换模型。

### 产出

- `assets/live2dcubismcore.min.js`（官方 Cubism Core，207KB，内嵌 wasm）
- `assets/pixi.min.js`（pixi.js 6.5.10）
- `assets/cubism4.min.js`（pixi-live2d-display 0.4.0 的 cubism4 构建）
- `models/manifest.json` — 模型清单 + 模型/动作中文名映射
- `README.md`、`.nojekyll`、`.gitignore`

### 关键技术结论（重要，避免重走弯路）

**1. Cubism Core 必须用官方 CDN 版本**
- `https://cubism.live2d.com/sdk-web/cubismcore/live2dcubismcore.min.js`（207KB，不依赖外部 wasm 文件）
- npm 上的 `live2dcubismcore@1.0.2`（150KB）**只支持到 MocVersion_42（Cubism 4.2）**，缺 `MocVersion_50`
- 官方 CDN 版含 `MocVersion_50`，且提供 `Moc.prototype._release`
- `pixi-live2d-display` 会调用 `moc._release()`，必须用它自带的那个 moc 对象

**2. pixi-live2d-display 0.4 的真实 API（文档没写，靠实测得出）**
```
internalModel.motionManager
  .motionGroups[groupName]        已解析动作对象数组，顺序与 definitions 一致
  .queueManager._motions[]        当前队列项
  .queueManager.startMotion(motionObj, false)   ← 指定动作的唯一可靠入口
  .queueManager._userTimeSeconds  当前时钟（秒）
  .updateMotion(coreModel, dt)    推进时钟 + 更新参数
  .definitions[group][i].File     动作文件路径
```
- **没有** `startMotionByIndex()`，**没有** `currentMotion` 属性
- 队列项：`getStartTime() / getEndTime() / isStarted() / isFinished() / _motion`
- `_motion.getDuration() / isLoop() / getLoopDuration()`
- **当前时间 = `queueManager._userTimeSeconds - entry.getStartTime()`**
- `motionManager.update(coreModel, deltaSeconds)` 内部就是 `_userTimeSeconds += delta`

**3. 缩放必须按 drawable 包围盒，不能按画布尺寸**
- 本模型 moc 画布是 **3000×3000**，但角色只占中间一小块 → 按画布缩放会让角色小得可怜
- 坐标换算（与 SDK `getDrawableVertices` 一致）：
  ```
  px = vx * pixelsPerUnit + originalWidth  / 2
  py = -vy * pixelsPerUnit + originalHeight / 2
  ```
- 顶点以画布中心为原点，y 轴向上；`pixelsPerUnit` 在 `internalModel.pixelsPerUnit`
- 定位时要减去「内容中心 − 画布中心」的差值，因为锚点 (0.5,0.5) 对的是画布中心

**4. 无头浏览器验证的坑**
- `gl.readPixels` 与 `canvas.drawImage` 在 headless 下**拿不到变化的帧**（返回陈旧缓冲），会导致误判"动画没在动"
- 可靠做法：页面用 `mm.updateMotion(cm, 1/30)` 推进到指定时刻 → `app.renderer.render()` → `app.ticker.stop()` 定格 → 用 Chrome `--screenshot` 抓图 → 比较两张 PNG 的像素差异
- 14 个动作全部实测有动画（差异 7%–21% 像素）

**5. 其它**
- 必须用 http(s) 打开（`fetch` 读 model3.json），`file://` 不行
- 动作时长从各 `motion3.json` 的 `Meta.Duration` 预读，用于列表显示和进度条
- 变速实现：直接给 `queueManager._userTimeSeconds` 追加 `(speed-1)` 倍增量
- 拖动进度条：`entry.setStartTime(clockSeconds() - ratio * duration)`

### 模型现状
- `models/aimierbeierding_2/`：14 个动作，2 张纹理（各约 1.2MB），moc3 约 587KB

**1. 三级降级发现（GitHub Pages 不支持列目录）**

- 统一数据结构：`{ path, file, name, group, parts, motions, textures, mocVersion, key, missing }`
- `key = path + '/' + file`，作为 localStorage 记忆的唯一标识（旧的按 name 匹配已废弃）
- 侧栏标题旁显示当前来源（`共 42 个 · models/index.json`），并用 `title` 提示

**2. ⚠️ `_userTimeSeconds` 是死字段（本轮最大发现，推翻第一轮的结论）**
读 minified 源码确认：
- `Cubism4MotionManager` 只有 `updateParameters(coreModel, t)`，**自身不累加时钟**
- 上层 `Cubism4InternalModel.update(t, e)` 传进来的是**每帧秒数**（≈0.0167），不是累计时间
- `queueManager.startMotion(motion, autoDelete, t)` 的**第三个参数被完全忽略**，队列项 `startTime` 恒为 0
- → 动作永远停在第一帧，但日志一切正常，极难排查

改法：**自己维护 `S.motionClock`**，每帧 `doUpdateMotion(coreModel, S.motionClock)`，
并把 `queueManager._doUpdateTime = S.motionClock` 对齐内部时间基。
当前时间 = `_doUpdateTime - entry.getStartTime()`。

**3. ⚠️ 还必须调 `internalModel.update()`，否则画面一个像素都不动**
`internalModel.update` 里除了动作还负责：表达式 → 眨眼 → 视线 → 呼吸 → 物理 → 姿态
→ **`coreModel.update()` + `loadParameters()`（把参数真正写进 drawable）**。
只调 `doUpdateMotion` 的话，参数只在内存里变，进度条正常走但画面完全静止。
传 `dt = 0` 避免它自己再推进动作；同时 `model.autoUpdate = false` 独占更新循环。

**4. 折叠树的一个隐蔽 bug**
`buildGroup` 里给 `group-head` 绑了 `click`，我又在 `modelList` 上做了事件委托 →
两次 toggle 互相抵消，表现为「点了没反应」（class 逻辑本身是对的）。
另外 `wrap.dataset.group` 一开始漏设，导致 `dataset.group` 是 `undefined`。
两处都已修。

**5. 无头验证方法升级：CDP 直连**
- `--screenshot` 只能截一张、无法交互。改用 Node 手写最小 WebSocket 客户端直连 CDP
- **握手响应后剩余字节就是第一帧**，必须存进帧缓冲再 `_drain()`，漏了会「所有命令都超时」
- 两种断言互补：
  - 时钟推进：两次采样 `info().clock` 差值
  - 画面真在动：`Page.captureScreenshot` 两次同区域，base64 不同才算通过
  - **时钟在走但截图完全一样 = 参数没提交到 drawable**（见第 3 点）
- Windows 上用 `&` 起的后台服务会随工具调用结束被回收，必须「起服务 + 起浏览器 + 断言」同一脚本跑完

## 追加：修复「动画人物持续快速抖动」（第三轮）

**现象**：模型播放时人物持续高频抖动，暂停后也在抖。

### 根因（三处，都在时间轴与定格逻辑上）

**1. ⚠️ 定格项 `setEndTime(holdTime)` → `doUpdateMotion` 整个空转（主因）**

`doUpdateMotion` 的实现是：
```js
update(t, e) { return !this.isFinished() && this.updateParameters(t, e); }
```
`isFinished()` 判定 `t >= endTime`。而第二轮写的定格是
`setStartTime(0); setEndTime(holdTime); _doUpdateTime = holdTime;` ——
求值时刻恰好等于 endTime，**一入队就 finished**，`doUpdateMotion` 直接 return，
动作参数一个都没写进去。结果不是「静止」而是「更会动」：姿势退回默认值，
呼吸/物理/眨眼这些每帧都在变的层继续在默认值上叠加 → 持续抖动。

修法：定格项的终点必须是**远超任何动作时长的常数**（`HOLD_END = 3600`），
起止时间只用来让 `doUpdateMotion` 别空转，实际位置靠 `_doUpdateTime` 控制。

**2. ⚠️ `internalModel.update` 的 dt 不能传 0（第二个抖动源）**

第二轮为了「只提交这一帧」写成 `im.update(performance.now(), 0)`。但
`internalModel.update(deltaMS, elapsedMS)` 里依次做：
motion → expression → eyeBlink → focus → breath → **`physics.evaluate(cm, dt)`** → pose
→ `cm.update()/loadParameters()`。

- `physics` 是按 dt 迭代收敛的弹簧系统 —— dt=0 让它**每帧停在同一中间态、永不收敛**
- `pose.updateParameters(cm, dt)` 的部件淡入淡出同样按 dt 累积

修法：`im.update(dt * 1000, 0)` —— **第一个参数给真实帧间隔，第二个仍给 0**
（elapsed 给真实值会和 `doUpdateMotion` 的时间基打架）。

**3. 只挂一次，绝不每帧重新入队**

定格项必须记在 `S.pausedEntry` 上，`mountHoldEntry` 开头 `if (S.pausedEntry) return;`。
每帧 `startMotion` 会让动作在起始姿势与末帧之间来回横跳 —— 也是抖动。

### 顺带修掉的两个交互 bug

- **定格后按播放没反应**：播完后 `S.playing` 仍为 `true`，第一次点「播放」被当成「暂停」。
  改为播完时 `S.playing = false` + `setPlayIcon()`。
- **暂停后按播放从头开始**：需要区分「中途暂停」（续播）与「自然播完/拖到末尾」（重播），
  新增 `S.finished` 标志。续播用 `resumeMotionAt(at)`：把 `_doUpdateTime` 设成 `at`
  并同步调一次 `doUpdateMotion(cm, at)`（因为 `startTime` 会被 SDK 首次
  `updateParameters` 重设成当时的 t，所以让 t 与 at 对齐即可无缝接上）。

- **循环动作会被误判成「播完」**：循环动作绕回起点瞬间 `isFinished()` 短暂为真，
  SDK 摘掉队列项再重新入队；「播完定格」分支若不排除循环动作，每绕一圈就把
  `playing` 置 false → 循环动作播一会儿自己停住、图标乱跳。
  已在分支条件加 `&& !isCurrentLoop()`。

### ⚠️ 抖动只有「参数快照」测得出来（验证方法的关键升级）

- `Page.captureScreenshot` 对 PNG 压缩噪声敏感 → 画面几乎没变也会得到不同 base64，
  只能证明「有变化」，**证明不了「没在抖」**
- `gl.readPixels` / `ctx.drawImage(canvas)` 在无头 Chrome 里读到的是过期缓冲（实测全 0）
- 可靠判据：读 `coreModel._model.parameters` 的 `P.values`，间隔 700ms 采样两次，
  统计变化数。某 138 参数模型：**正常播放 82–104 个在变；暂停/定格/拖动定位后必须为 0**。
- 这个判据直接把 bug 从「88/138 在变」定位到「0/138」。

### 实测验收结果（26/26 通过，连跑两轮稳定）
页面就绪 / 点击动作起播 / 播放中参数在变 / 暂停冻结时钟与参数 / 中途暂停不算播完 /
暂停后按播放是续播 / 拖动定位精确且参数冻结 / 定格项终点为大值 /
拖动后按播放能重开 / 自然播完进入定格 / 播完 finished=true 且 playing=false /
定格后按播放重播 / 连续切换 6 支不卡死 / 换模型后正常播放 / 换模型后暂停仍能冻结 / 无 JS 异常

## 第二轮：用户报 4 个 BUG 的真实根因（推翻了上一轮的部分结论）

用户报告：`#1 切模型后不自动播放`、`#2 zhala_2 播放错位`、`#3 bisimai_2 播放错位`、
`#4 隐藏动作列表 + 切模型后自动连播全部`。

### ⚠️⚠️ 上一轮「26/26 通过」是假通过 —— 判据本身失效

上一轮把「暂停后参数变化数 = 0」当成验收铁律。但 `weight = 0`（错位）时
**动作参数本来就一个都不写**，所以「参数变化数」在「正确定格」和「错位」下**同为 0**。
测试被 bug 满足，从未验证过动作本身是否被应用。

**新的主判据：队列项权重 `entry.getStateWeight()` 必须收敛到 `1`。**

| 场景 | `getStateWeight()` | 参数变化数 |
| --- | --- | --- |
| 正在播放 | `1` | 明显 > 0（138 参数约 85） |
| 正确定格 / 暂停 | `1` | `0` |
| **错位** | **`0`** | 播放中也接近 0 |
| **定格时 fadeInStartTime 没往回拨** | **`0`** | `0` |

### ⚠️⚠️⚠️ 错位唯一根因：`im.update` 的第二个参数（elapsedMS）

上一轮写的「elapsed 必须传 0」**是错的**。正解：

```js
im.update(dt * 1000, S.motionClock * 1000);
//         ↑ 真实帧间隔   ↑ 必须等于动作时间轴位置
```

`Cubism4InternalModel.update(deltaMS, elapsedMS)` 里 `motionManager.update(cm, e)`
→ `queueManager.doUpdateMotion(cm, e)`，会**在我们刚用 motionClock 写好参数之后，
再用 elapsed 求值并覆盖一次**。传 0 时时间 0 处 `ease(0) = 0`
→ `weight = 0` → `参数 = 当前值 + (目标值-当前值)*0 = 当前值` → 动作一个参数都没写进去，
画面只剩呼吸/物理/姿态 → 即「时间轴在走、姿势对不上」的**错位**。

口诀：**错位看 elapsed，微抖看 delta。**

### 权重为 0 的三大来源（现象完全相同，别只修一个）

1. `im.update` 的 `elapsedMS` 传 0
2. 定格/暂停时 `fadeInStartTime == 求值时刻` → `ease(0)=0`。
   必须 `setIsStarted(true)` 阻止 SDK 首次求值重设，再
   `setFadeInStartTime(holdTime - fadeInSec - 0.001)`
3. **连续切换模型**：新模型上舞台到 `playMotion` 之间，`tickProgress` 用
   **上一个模型遗留的 `S.motionClock`**（如 15.13）初始化新队列项
   → `startTime = fadeInStartTime = 15.13`
   → `t - fadeInStart = 0.67 - 15.13 < 0` → 权重永久 0。
   修法：新增 `S.primed` 门控（`loadIntoStage` 置 false，`playMotion` 末尾置 true）

### ⚠️⚠️ 这个 SDK build 的 `_isLoop` 恒为 false —— 循环必须自己实现

`assets/cubism4.min.js` 里 `setIsLoop(` **只有方法定义、全文件没有任何调用点**。
所以 `Cubism4Motion` 的 `_isLoop` 永远是构造时的 `false`，与 `motion3.json` 的
`Meta.Loop` 毫无关系。后果：

```js
getDuration() { return this._isLoop ? -1 : this._loopDurationSeconds; }  // 永远返回真实时长
// 到时：this._isLoop ? 绕回起点 : (setIsFinished(true) + 被 splice 出队列)  // 永远走 else
```

即 `Idle` 这类动作**播一遍就停住**，不是「一直循环」。

修法：`S.motions[i].loop`（扫 model3.json 时读 `Meta.Loop`）是唯一权威来源；
`isCurrentLoop()` 优先用它，**不要**读 SDK 的 `isLoop()`。
`tickProgress` 里队列空了 + 是循环动作 + 在播 → 自己 `playMotion(S.current, true)` 重播。

连播时循环动作没有「播完」时刻，必须用 `LOOP_DWELL = 6s` 计时推走，否则永远卡在 Idle。

### 其它修复

- `setIsStarted(true)` 后 SDK 不再补 `endTime` → 必须显式
  `setEndTime(motionObjectDuration(motionObj, mo))`，否则 `isFinished()` 永假，
  「播完自动下一个 / 连播」永不触发
- `findMotionObject`：`mm.getMotionFile()` 只接受**定义**对象，而 `motionGroups[group]`
  里是**已加载的动作对象**（无 `.File`）。要按文件名反查得走 `mm.definitions[group][i].File`
- `switchModel` 的 `busyModel` 互斥原来直接 `return`，用户连点会觉得「点了没反应」。
  改为记 `S.pendingModel`，载完由 `drainPendingModel()` 补切
- 新增 `window.__viewer.switchedTo(key)`，自动化测试要等它变 true 再采样

### 新增功能（#4）

- **连播全部动作**：`startPlayAll / stopPlayAll / tickPlayAllLoopDwell`，
  切模型后从第 1 个依次播完；手动选动作自动退出（`userPlay`）
- **隐藏动作列表**：`.sidebar.no-motions` 让模型列表占满侧栏
- **`?model=` 深链**：`wantModelFromURL()`，便于分享与测试

### 验收方法学的三个坑（都已踩过）

1. **不要用固定 sleep 断言「播放中权重=1」** —— 无头 Chrome 的 rAF 比墙钟快，
   5 秒动作 2 秒就播完并摘掉队列项，此时 `entry=null` 是「播完了」不是「错位」。
   要**逐帧采样整个播放过程**，记录**最大权重**（应到 1）与**最大时钟**（应 > 0.5）。
   采样循环必须有硬上限（如 300 帧）否则永不 resolve 会卡死整套测试。
2. **`switchModel` 有 `busyModel` 互斥** —— 连续调用第二次会被 return，
   你测的其实还是上一个模型。
3. **测连播要挑动作短的模型** —— `biaoqiang` 平均 3.64s 最合适；
   `zhala_2` 平均 13.44s，观察 14 秒当然只看到 1 个动作。

### 最终验收（`_regress.js`）

三个模型权重均到 1 / 时长一致 / 时间轴推进 / 参数在变；
切模型后 playing=true 从第 1 个动作开始；
隐藏动作列表 + 连播推进 0→6；
暂停定格权重=1 且参数冻结、续播不回 0、拖动定位权重=1；
**循环动作 20 秒重播 4 次且 playing 保持 true**、非循环播完不重播且进入定格；

### ⚠️⚠️⚠️ 本轮最大发现：动作对象是异步加载的，切模型后队列可能永久为空

**现象**：`biaoqiang`（动作组名是空串 `''`）切过去后**永久不播** ——
`qlen=0, clk=0, cur=0, retry=0, playing=true`，界面看着正常，就是不动。
而 `zhala_2`（组名 `Start/Idle/...`）完全正常。

**排查过程**（7 个探针脚本，逐步缩小）：
1. 探针 1：`biaoqiang` 一直 `qlen=0`，`zhala_2` 正常 → 与模型相关，不是全局问题
2. 探针 2：**从 devtools 控制台**（click 事件，与 rAF 无关）切 biaoqiang → 完全正常
   （`qlen=1, w=1`）→ 是**时序问题**，不是模型数据问题
3. 探针 3：挂 `playMotion` 钩子 → 切模型时 `playMotion` 没被重入；
   切完 4s 后手动 `playMotion(0)` 立刻 `qlen=1, w=1` → 排除 `reserve` 路径
4. 探针 4/5：异步稳定复现（一直 `qlen=0`），手动调立刻成功
5. 探针 6（页面内 200ms 采样器）：`retry` 恒为 0 → **原本的「定时重试」根本没生效**
6. 探针 7：给 `queueManager._motions` 装 setter → **没抓到任何 `set _motions` 事件**

**根因**（探针 7 的结论 + 源码对照）：
- `motionPreload:'ALL'` 是**异步**的 —— `setupMotions` 先把 `motionGroups[group]`
  全置成空数组，再逐个 `loadMotion().then()` 填回去。
  `loadIntoStage` resolve 的那一瞬间 `findMotionObject()` 返回 `null`。
- 而 `playMotion` 拿不到 `motionObj` 时会走兜底重试；这条路径在当时有闭包/时序问题，
  实测没生效（`retry` 恒 0）。
- **更阴的一层**：`motionManager()` 在 `S.l2dModel` 还是旧模型时返回**旧 mm**，
  于是 `stopAllMotions()` 打偏。若新旧模型**组名 + 文件名相同**
  （biaoqiang 和上一支都是 `''` 组 + `motions/complete.motion3.json`），
  `reserve` 检查不冲突，动作还能成功启动到**旧模型的队列**上 ——
  `activeEntry()` 非空、看起来"启动成功"，但**新模型队列永远是空的**。

**修法**：放弃一次性定时重试，改成**渲染循环里自愈**：
```js
var START_RETRY_MS = 300;
var lastStartAt = 0, startRecoveryCount = 0;

function tickStartRecovery() {
  if (!S.playing) return;                        // 暂停时不打扰
  if (activeEntry() || S.pausedEntry) return;     // 队列里有东西 = 正常状态
  if (Date.now() - lastStartAt < START_RETRY_MS) return;
  lastStartAt = Date.now();
  startRecoveryCount++;
  playMotion(S.current < 0 ? 0 : S.current, true);
}
```
`tickProgress` 里：`if (!holding && !e && !S.pausedEntry) tickStartRecovery();`
**不设次数上限** —— 动作一可用就自动接上。`playMotion` 末尾记 `lastStartAt = Date.now()`。
诊断入口：`window.__viewer.info().startRecoveryCount`。

回归从 53 通过 / 4 失败 → **57 通过 / 0 失败**。

### 2. zhala_2 故障根因：SDK 自己会偷偷起 Idle 动作

现象：`login`(22.33s) 播完后**每 12 秒**（正好是它 Idle 的时长）自己重启一次，永远停在第一个动作。

`assets/cubism4.min.js` 的 `MotionManager.update()` 里写死了：

```js
this.state.shouldRequestIdleMotion() && this.startRandomMotion(this.groups.idle, IDLE)
// shouldRequestIdleMotion() { return currentGroup === undefined && reservedIdleGroup === undefined }
```

**只要动作队列空了，SDK 就自己从 Idle 组随机起一个动作。** 它插入的队列项 `startTime`
是在首次求值时写成「当时的 elapsed」的 → `currentTime() = elapsed - startTime` 恒为 0 → 页面永远等不到「播完」。

定位手段：`_probe_monitor.js` 逐行 dump 发现「`cur` 不变、`clk` 一路涨、每 12 秒 `eStart` 被刷成新值」；
`_probe_trace.js` 给 `queueManager.startMotion` 装钩子抓调用栈，抓到 `ze._startMotion → cubism4.min.js` —— **不是页面代码**。

修法（三重保险，缺一个都可能漏）：
```js
var NO_IDLE_GROUP = '__no_auto_idle__';
function disableAutoIdle(mm) {
  try { mm.stopAllMotions(); } catch (e) {}
  mm.groups && (mm.groups.idle = NO_IDLE_GROUP);
  mm.startRandomMotion = function () { return false; };
}
// 装载时还要传 idleMotionGroup: NO_IDLE_GROUP
```

> ⚠️ **`idleMotionGroup` 传空串等于没传** —— SDK 是 `(t?.idleMotionGroup) && (...)`，空串是 falsy。

### 3. 修完 Idle 后暴露的三个次生 bug（其实一直都在）

1. **队列空时 `tickProgress` 不推进时钟** → SDK 摘掉队列项后时间轴冻结，「播完自动下一个」永不触发。去掉 `&& e`。
2. **`S.playing = false` 死锁**：`mountHoldEntry` 拿不到动作对象时 `return`，调用方却无条件置 `S.playing=false`
   → 页面永久停住，`tickStartRecovery` 又被 `if (!S.playing) return` 挡住。加 `if (S.pausedEntry)` 守卫。
3. **「动作没启动起来」被误判成「播完了」** → 加 `stalled` 门控 + `S.holdTime >= dur - 0.05` 条件。

### 4. ⚠️ `Meta.Loop = true` 不等于「要循环播」

zhala_2 的 **全部 15 个动作**都标了 `Meta.Loop = true`。之前按「循环动作 → 用固定 `LOOP_DWELL = 6s` 推走」，
于是 wedding(31.17s) / login(22.33s) / home(20.17s) 全在第 6 秒被硬切。
正确语义：**不管 `Meta.Loop` 是什么，都完整播一遍自己的时长。**
`LOOP_DWELL` / `loopEnterAt` / `loopEnterIndex` / `tickPlayAllLoopDwell()` 已全部删除。

### 5. ⚠️ PIXI ticker 的 delta 已按 60fps 归一化 → 换算成秒是 `delta / 60`

```js
this.deltaMS   = t - lastTime;                 // 真实帧间隔（毫秒）
this.deltaTime = this.deltaMS * TARGET_FPMS;   // TARGET_FPMS = 0.06 = 1/16.667
n.emit(this.deltaTime);                        // 回调收到的就是这个
```
**绝不能除以 `ticker.FPS`** —— 那是「实测帧率」（144/165/240），会让动作按 `60/实测帧率` 倍慢放。
60Hz 屏上完全看不出来，只在高刷屏暴露。修完实测 1.002×（后续复跑 0.995×）。

### 6. ⚠️ 截图不能用来判断舞台背景色

三档截图（浅/深/黑）里舞台**全是黑的**，一度怀疑 CSS 有问题。实测：
- `getComputedStyle(stage).backgroundImage` 三档值**完全正确**
  （浅 `radial-gradient(...rgb(255,255,255)...)` / 深 `rgb(43,52,68)` / 黑 `rgb(0,0,0)`）
- `pixiBgAlpha: 0` → canvas 本来就是透明的
- **把 `#live2d-canvas-host` 隐藏后再截图 → 浅色舞台立刻是正常的白色径向渐变**

结论：**无头 Chrome（swiftshader）在 `Page.captureScreenshot` 时把 WebGL canvas 的透明区域合成为黑色。**
页面没问题，是截图环节的假象。**以后验证背景色一律读 `getComputedStyle`，不要看截图。**
